## 2026-07-23 — v0.2.0 ⭐ 이벤트 뉴스 히스토리 백필

### 배경
첫 실전 데이터 확인 결과, 몇 달 전 급등락일(예: 삼성전자 -12.3%)에는 매칭된
뉴스가 없어 "뚜렷한 개별 뉴스를 찾지 못했습니다"만 표시됨. 우리가 수집하는
RSS는 최근 뉴스만 담기 때문. R5(차트-뉴스 연동)의 핵심 가치가 최근 이벤트에만
작동하는 한계.

### 변경
- **날짜 지정 Google News 백필 추가** — Google News RSS의 `after:/before:`
  연산자로 특정 과거 날짜의 뉴스를 가져와, 뉴스가 없는 이벤트에 붙임.
  국장은 `"종목명" after:.. before:..`, 미장은 `"CompanyEn" stock after:.. before:..`.
  실측: 삼성전자 2026-06-23(-12.3%)에 "삼성전자 주가, 오늘 왜 급락했을까?" 매칭됨.
- **비용 제한** — 종목당 최대 6개(고심각도·뉴스없음 우선), 200일 이내 이벤트만.
  60종목 × 6 × 1.2s ≈ 7분 추가. `EVENT_NEWS_BACKFILL` 플래그로 on/off.
- **초보모드 이벤트 필터 개선** — severity≥2 뿐 아니라 "뉴스가 매칭된 이벤트"도
  노출. 최근의 설명 가능한 이벤트가 숨겨지던 문제 해결 (web).
- **NewsCard 중첩 앵커 버그 수정** — 카드 루트를 `<a>`→`<div>`로 변경.
  종목 칩 링크가 앵커 안에 중첩되어 hydration 오류 발생하던 문제 (web).

## 2026-07-28 — 브리핑 발송 시각을 "개장 30분 전"으로 재설계

### 문제 — GitHub 스케줄러 지연
사용자 요구는 "장 시작 전 전송"인데(2026-07-22 요구사항), 미장 브리핑이 개장 후에 도착했다.
원인은 **cron 시각 자체가 아니라 GitHub 스케줄러가 예약 시각을 안 지키는 것**이다. 실측:

| 워크플로 | 예약 | 실제 run 생성 | 지연 |
|---|---|---|---|
| brief-kr (2026-07-26) | 22:30 UTC | 23:27:24Z | **+57분** |
| brief-us (2026-07-27) | 12:30 UTC | 15:23:02Z | **+173분** |

`run_started_at == created_at`이므로 concurrency 큐 대기가 아니라 스케줄러 자체의 지연이다.
GitHub은 정각·30분에 스케줄이 몰릴 때 예약 실행을 밀거나 아예 드랍한다(문서화된 동작).
brief-us는 7/27이 워크플로 생성 후 첫 평일 슬롯이었는데 173분 밀려 **개장 2시간 뒤**인
00:34 KST에 발송됐다.

부차 원인 하나 더: 기존 시각 계산에 **job 실행 시간이 빠져 있었다.** `--rebuild` 탓에
실제 소요가 11~19분(brief-us 11m24s, brief-kr 18m45s 실측)이라, cron이 정시에 떠도
메시지는 그만큼 뒤에 나간다.

### 변경 — 다중 슬롯 + 시각 게이트
단일 cron으로는 도착 시각을 보장할 수 없으므로 구조를 바꿨다.

1. **슬롯 다중화** — 하나가 밀려도 다음 슬롯이 제시간에 뜰 확률을 남긴다.
   - `brief-kr`: `11 23 * * 0-4`, `23 23 * * 0-4` (08:11 / 08:23 KST 시작)
   - `brief-us`: `41 12`, `53 12`, `41 13`, `53 13` `* * 1-5` (08:41 / 08:53 ET 시작)
   - 슬롯 = 목표 도착시각 − 빌드 시간. 정각·30분은 피했다.
2. **발송 창 게이트** — 실제 로컬 시각이 창 밖이면 체크아웃 전에 즉시 종료.
   KR `08:05~08:35 KST`, US `08:35~09:05 ET`. → 늦게 뜬 실행이 개장 후 브리핑을 쏘지 않는다.
3. **중복 발송 게이트** — `data/brief/{세션일자}-{시장}.json`이 이미 있으면 종료.
   슬롯끼리는 같은 concurrency 그룹이라 병렬로 겹치지 않으므로, 먼저 성공한 슬롯의
   커밋을 뒤 슬롯이 체크아웃해서 보게 된다.
4. **미장 서머타임** — cron은 UTC 고정이라 DST를 못 따라간다. EDT/EST 양쪽 슬롯을 모두
   예약하고 계절이 어긋난 쪽은 창 게이트가 걸러낸다(07:41 ET 또는 09:41 ET로 뜬다).
5. **푸시 재시도** — 커밋 스텝을 pulse와 동일하게 `git pull --rebase --autostash` 3회
   재시도로 통일(봇 커밋 경합 대비).

`workflow_dispatch`는 두 게이트 중 창 게이트를 항상 통과한다(수동 테스트용).

### 남는 한계

## 2026-07-28 — v0.5.0 ⭐ 스케줄러 지연에 견디는 브리핑 발송

### 증상 (사용자 신고 3건)
1. 금일 장 시작 30분 전 텔레그램 브리핑이 **안 옴**
2. 웹 브리핑도 **월요일에서 멈춤**
3. 다른 뉴스 수집은 정상인지 확인 필요

### 원인
코드 버그가 아니다. **슬롯 배치 문제.** `gh run list` 실측:

```
brief-kr  23:11 UTC 예약 → 00:09:40Z 시작 (+58분) → 09:09 KST → 발송 창 밖, 차단
brief-kr  23:23 UTC 예약 → 00:14:22Z 시작 (+51분) → 09:14 KST → 발송 창 밖, 차단
```

발송 창 게이트는 **설계대로** 동작해 개장(09:00) 후 발송을 막았다. 문제는 슬롯이
2개뿐이라 둘 다 밀리면 그날은 아예 발송이 없었다는 것. 이 저장소의 스케줄러 지연은
`+6 ~ +202분`으로 널뛴다(pulse +114, brief-us +173, data-sync +202 실측).
옛 배치는 0~240분 지연 중 **30개 구간(12%)만** 커버했다.

②는 ①의 결과다. Vercel 배포와 `cache: "no-cache"` fetch 모두 정상이었고,
브리핑 JSON 이 생성되지 않아 웹이 옛 파일을 계속 그린 것뿐이다.

③은 정상이었다. `doctor` 결과 매크로 12/12, RSS 19 정상 / 1 죽음(`yna_market`).

### 변경
- **`pipeline/gate.py` 신설** — 발송 판정(수동 강제 → 휴장일 → 중복 → 발송 창)을
  셸에서 파이썬으로. `python -m pipeline.run gate --market KR`. `pip install` 전에
  돌아야 하므로 **표준 라이브러리만** 쓴다.
- **`config.BRIEF_WINDOW`** — 발송 창을 설정화. 개장 75분 전 ~ 20분 전
  (KR `07:45~08:40 KST`, US `08:15~09:10 ET`). 기존 30분 → 55분.
- **슬롯 재배치** — KR 2 → **7개**(19:20~23:20 UTC), US 4 → **9개**(08:40~14:00 UTC),
  둘 다 40분 간격. 슬롯 간격(40분) < 발송 창(55분)이라 지연 0~240분 전 구간이 덮인다.
- **발송 경로에서 `--rebuild` 제거** — `pulse --market X` → `brief --send`.
  잡이 11~19분 → **37초**(실측). 슬롯을 3.5배로 늘렸는데도 사용 분은 줄었다.
- **브리핑 concurrency 분리**(`stock-pulse-brief-KR|US`) — 26분짜리 `data-sync` 뒤에
  큐잉되면 발송 창을 통째로 놓칠 수 있었다.
- **스케줄 잡 전부 `checkout ref: main`** — 스케줄 트리거는 예약 시점 SHA 를 준다.
- **`.github/scripts/commit-data.sh`** — 네 워크플로의 커밋·푸시 통일. 거절 시
  `rebase -X theirs` 후 재시도(5회). 기존 `pull --rebase`는 충돌 시 데이터를 날렸다.
- **발송 실패 시 exit 1** — 브리핑 파일이 커밋되지 않아 남은 슬롯이 자동 재시도한다.
- **리허설 모드** — `workflow_dispatch` 입력 `send=false`면 발송도 커밋도 하지 않고
  빌드·렌더링만 확인한다. 텔레그램을 건드리지 않고 경로를 점검할 수 있다.
- **죽은 피드 `yna_market` 제거** — 피드 20종 → 19종(KR 9 + US 10).

## 2026-08-02 — v0.6.0 ⭐ 차트 분석 (기술적 분석 신호)

### 요구사항 (사용자)
- 주식 차트 분석 기법들을 기반으로 내용을 정리해 **브리핑과 차트창에 추가**
  (예: 추가매수 신호 / 매매 신호 / 추격 신호)
- **도움말에 차트분석 탭** 추가 — 예시 차트 이미지와 내용 정리

### 변경

**`analyze/technical.py` 신설** — 널리 쓰이는 기법 11가지를 한 모듈에 모았다.
정배열/역배열 · 골든/데드크로스 · 이격도 · 60일선 기울기 · MACD · RSI · 볼린저밴드
· 스토캐스틱 · 거래량 · 신고가/신저가 돌파 · 지지·저항 근접. 각각
`bullish|bearish|neutral` + 세기(0~1) + 가중치(1~3)로 판정하고 가중 평균해
`-100~+100` 종합 점수를 낸다.

- **중립 판정도 분모에 넣는다.** 그래야 11개 중 2~3개만 강세인 종목이 강한
  신호로 둔갑하지 않는다. 실측에서 미장 184종목의 점수 중앙값이 0.5로 잡혔다.
- **행동 신호를 점수와 따로 둔다.** 같은 "매수 우위"라도 이미 크게 오른 자리인지
  눌린 자리인지가 점수로는 구분되지 않는데, 사용자가 실제로 궁금한 건 그 차이다.
  8가지: 추격 · 추가매수(눌림목) · 매수전환 · 차익실현 · 비중축소 · **손절유의** ·
  반등확인 · 관망. **손절이 1순위** — 좋은 신호와 겹쳐도 손실 관리를 먼저 보여준다.
- **LLM을 쓰지 않는다.** 결정론적 pandas 계산이라 같은 입력에 늘 같은 답이 나오고,
  184종목 전체가 sync 한 번에 8~11초다. 무료 Gemini 쿼터는 이벤트 해설 몫으로 남는다.
- 임계값은 교과서 관습값 그대로(RSI 70/30, 20×60일선 크로스). **과거 데이터에 맞춰
  최적화하지 않았다** — 과거에 맞춘 값이 앞으로도 맞는다는 보장이 없고, 초보
  사용자가 다른 앱에서 본 숫자와 어긋나면 설명만 어려워진다.

**차트창** — 지표 토글 6종(뉴스마커·이동평균·볼린저·MACD·RSI·지지저항). MACD·RSI는
가격과 단위가 달라 lightweight-charts v5의 별도 pane에 올린다. 지지·저항은
`createPriceLine()`으로 가로줄. 기본값은 뉴스마커·지지저항만 ON — 처음 열었을 때
선이 많으면 초보자가 아무것도 못 읽는다.

**분석 카드** — 점수가 아니라 **행동 문구가 주인공**이고, 그 아래 근거가 된 기법
11줄이 붙는다(누르면 "왜 그렇게 읽는지" 펼침). 점수 하나만 크게 보여주면 근거 없는
점괘가 된다. 초보모드에서는 방향이 잡힌 4개만 먼저 보여준다.

**브리핑** — `chartSignals`(강세/약세 각 4종목 + 시장 전체 카운트)를 웹·텔레그램
양쪽에 추가. `index.json`의 압축본을 모을 뿐이라 재계산이 없다. 3줄 요약 프롬프트에도
차트 요약 한 줄을 넣되, **매수·매도를 권하는 문장으로 바꾸지 말라**고 못박았다.

**도움말 탭** — 봉 해부도 → 기법 11가지 → 합산 방식 → 행동 신호 8가지 → 한계 4가지.
각 기법은 "무엇을 재나 / 예시 차트 / 읽는 법 / **언제 틀리나**" 4단이다.
예시 차트는 **캡처 이미지가 아니라 SVG**다 — 이미지는 ①테마 전환에서 어색해지고
②폭이 줄면 글씨가 뭉개지며 ③실제 차트 색이 바뀌면 조용히 어긋난다. 값 배열을 두고
이동평균·볼린저·RSI·MACD·스토캐스틱을 TS로 실제 공식대로 계산해 그린다.

### 규제 판단
"추격 매수 신호" 같은 문구는 **기술적 분석 교과서가 그 차트 모양에 붙인 국면
이름을 옮긴 관찰**이며 권유가 아니다. 이 전제를 지키려고 세 가지를 항상 같이
내보낸다 — ①근거(지표 11가지 수치) ②한계(`actionNote`·`disclaimer`·도움말 한계 절)
③가격만 본 계산이며 실적·공시는 반영하지 않는다는 사실. 목표가·비중·진입 시점은
어느 경로로도 만들지 않는다(비목표 유지).

### 화면에서 잡은 것 (브라우저 확인)
- **보조 패널이 27px로 찌그러졌다.** lightweight-charts v5의 pane 높이는 픽셀이
  아니라 **비율**이다. `pane.setHeight(110)`은 다음 pane이 추가되는 순간 재분배돼
  무시된다. `setStretchFactor()`로 바꿨다.
- **지지선이 현재가 −42%에 찍혔다.** 스윙 피벗만 후보로 쓰면 한 방향으로만 흐른
  구간에서 거의 안 잡힌다(상승장에서는 정의상 골짜기가 안 생긴다). SK하이닉스가
  800k→3.2M 오른 뒤 조정 중일 때 넉 달 전 808,000이 뽑혔다. 최근 20봉의 고·저를
  후보에 같이 넣고 **가장 가까운 것**을 고르게 했다(지지선 거리 중앙값 3.6%).
  후보가 없으면 `null` — 신저가 종목에 없는 지지선을 만들어 내지 않는다.
- **도움말 RSI 예시선이 패널 밖으로 새어 나왔다.** `min/max`를 직접 준 보조
  패널은 값이 그 밖으로 나갈 수 있어 클램프가 필요했다.
- **행동 신호 칩 색을 종합 점수 구간에서 뗐다.** 점수 −10(중립)인데 데드크로스로
  행동은 "비중 축소"인 종목에서, 회색 칩에 축소 문구가 붙어 읽히지 않았다.
  칩 색은 행동(`ACTION_TONE`), 숫자 색은 점수로 분리했다.
- MACD 히스토그램 표기 — 원화 종목은 네 자릿수라 `-5398.25`가 읽히지 않았다.
  자릿수 구분을 넣고 100 이상이면 소수점을 버린다.

### 도움말 예시 차트를 캔들로 (사용자 피드백)
"그냥 선이라 잘 모르겠다" — 맞는 지적이다. **봉 읽는 법을 가르치는 페이지의
그림이 선**이었으니 앞뒤가 맞지 않았다. 11개 예시를 전부 캔들로 바꿨다.

문제는 폭이다. 기존 예시는 90~95봉이라 그대로 캔들로 그리면 봉 하나가 2px
실선이 된다. 그렇다고 봉 수를 줄이면 60일선(60봉을 먹고 시작)이 화면 오른쪽
3분의 1에만 나타나 설명이 어그러진다. **시리즈는 130봉으로 계산하고 마지막
55봉만 그리는** 방식으로 풀었다 — 종목 차트가 기간 칩으로 하는 일과 같다.

곁들여 고친 것:
- 마커 좌표를 하드코딩에서 계산(`crossIndex`/`firstAbove`)으로 바꿨다. 파형을
  손볼 때마다 점선이 엉뚱한 봉에 찍히는 걸 실제로 겪었다.
- MACD 예시는 별도 파형으로 분리. MACD(12/26)는 이동평균 크로스보다 빨리
  반응해서, 골든크로스용 파형을 그대로 쓰니 정작 설명할 상향 교차가 보이는
  구간 밖에서 끝나 있었다.
- 마커를 원에서 삼각형(강세 아래·약세 위)으로. 캔들 위에 원을 얹으면 봉을 가린다.

### 지표 색을 시각적으로 (사용자 피드백)
"5일선·20일선·60일선이 어떤 색인지도 보여줘야 초보가 안다" — 맞다. 캡션에
"주황 5일선"이라고 **글로 적는 것으로는 부족**하다. 주황과 노랑, 보라와 남색은
말로 구분되지 않는다. 색 견본을 실제로 그려서 보여준다(`LineSwatch`).

- 종목 차트와 도움말 예시가 **같은 상수**(`lib/signals.ts`의 `INDICATOR`)를 본다.
  양쪽이 각자 하드코딩하고 있던 탓에, **초보모드의 20일선만 주황**으로 그려져
  도움말의 "보라 20일선"과 화면이 어긋나 있었다. 이제 초보/고급 모두 보라다.
- 범례는 **패널별로 줄을 나눈다**(가격 / MACD 패널 / RSI 패널). RSI·%K가 MA20과
  같은 보라를 쓰는데(별도 패널이라 차트에서는 안 겹친다), 한 줄에 늘어놓으니
  같은 색이 나란히 서서 서로 관련 있는 선처럼 보였다.
- 도움말 차트분석 탭 맨 앞에 **지표 색 약속** 절을 두었다. 8종을 색 견본 + 이름 +
  "그래서 뭘 보는 선인지"(예: 20일선 = 최근 한 달, 눌림목 기준선)로 한 번에 정리.
- 점선/실선도 차트와 똑같이 그린다 — 볼린저 위아래 선, MACD 시그널선, %D가 점선.
  (그 김에 종목 차트의 MACD 시그널선도 실선 → 점선으로 맞췄다.)

### 잡은 버그
`Series.replace(0, pd.NA)`는 series를 object dtype으로 만들어 뒤의
`rolling().mean()`을 `No numeric types to aggregate`로 죽인다. 14일 내내 값이 같은
얇은 ETF가 실제로 여기에 걸렸다. 분모 0은 `float("nan")`으로 둔다(RSI에도 같은
패턴이 있어 함께 고쳤다 — 그쪽은 죽지는 않고 FutureWarning만 뱉고 있었다).
`tests/test_technical.py::test_flat_prices_do_not_crash`가 재발을 막는다.

않은 채 남아 다음 실행까지 막는다. `-Quiet` 이 이 대기를 건너뛰고 `.sync-data.log`
(500줄 유지)에만 남긴다. 같은 이유로 `ExecutionTimeLimit` 30분 +
`MultipleInstances IgnoreNew`.

`StartWhenAvailable` 이 없으면 노트북은 사실상 주말마다 건너뛴다 — PC 가 꺼져 있어
시각을 놓치면 그냥 넘어가기 때문이다.

## 2026-08-04 — 추세선 + 52주 고·저 대비 위치

### 변경
사용자 요청 2건.

**추세선** — 스윙 저점 2개(상승)/고점 2개(하락)를 이어 마지막 봉까지 연장한
대각선. 수평 지지·저항이 "얼마"를 본다면 이쪽은 **기울기**를 본다. 기법별
판정에 12번째로 들어가고(`trendline`), 차트에 그려지며, 도움말 탭에도
같은 알고리즘으로 그린 예시가 붙는다. 183종목 중 160개(87%)에서 잡힌다.

**52주 고·저 대비** — `levels` 에 `high52Pct`(전고점 대비) ·
`low52Pct`(전저점 대비) · `rangePos`(저점~고점 구간의 몇 % 지점) 3개 추가.
셋 다 같은 재료지만 답하는 질문이 다르다 — "회복까지 얼마" / "바닥에서
얼마나 왔나" / "위쪽인가 아래쪽인가". 분석 카드에 게이지로 붙는다.

### 짚어둘 것
추세선에서 어려운 건 선을 긋는 게 아니라 **긋지 않는 것**이다. 아무 두 점이나
이으면 늘 선이 나오지만 사람이 차트에 그어 보는 선과 다르면 근거로 못 쓴다.
버리는 조건 셋:

1. **연장 상한** — 그은 구간보다 멀리 늘이지 않는다. 처음 구현에서 삼성전자의
   2~3월 고점 두 개(20봉 간격)가 8월까지 93봉 연장돼 현재가 대비 −58% 인
   "저항선"으로 나왔다.
2. **깨고 나서 오래 지났으면 죽은 선** — 반대편에 `TA_TREND_BREAK_GRACE`(10)
   봉 넘게 머물렀으면 버린다. 단, **끝에서 이어진 위반은 따로 센다** — 안 그러면
   "방금 이탈"(=알리려는 신호)과 몇 달 전에 죽은 선이 같은 값으로 나온다.
   처음엔 한 덩어리로 세서 삼성전자·SK하이닉스의 갓 발생한 이탈이 통째로
   사라졌다.
3. **애초에 안 지켜진 선** — 중간 구간에서 30% 넘게 뚫렸으면 버린다. 봉이
   `TA_TREND_MIN_APART` 개 미만이면 판정하지 않는다(3봉 중 1봉이면 33%지만
   그걸로 유효성을 말할 수 없다).

같이 고친 것: `_summary()` 가 "11가지 차트 기법 중…"을 상수로 박고 있었다.
판정기는 재료가 없으면 `None` 을 내므로 종목마다 실제 신호 수가 다르다 —
`len(signals)` 로 바꿨다.

### 잡은 버그

08-03 22:58 UTC (18:58 ET)  quote 2026-08-03  303.42   ← 정상

`_no_backslide()` — 새로 받은 마지막 봉이 이미 가진 것보다 과거면 저장된 봉으로
되돌린다. 소스를 못 믿을 때의 마지막 방어선이다. 지수(`macro.collect`)에도 같은
가드를 걸었다.

### 짚어둘 것
**빼 버리면 안 된다.** 처음엔 회귀를 감지하면 그 종목 빌드를 건너뛰게 했는데,

교체하므로 종목이 `index.json` 에서 사라져 검색·목록에서 없어진다. 지수도
마찬가지로 `_build_overview` 가 `indices` 를 통째로 갈아끼운다. 낡은 값은
불편하지만 사라진 종목은 고장이다 — 그래서 둘 다 **이전 값을 이어받는다**.

## 2026-08-04 — 마감과 갱신 사이 공백: 슬롯 다중화 + 화면에 기준일 표기

### 잡은 문제
"장 마감 가격으로 갱신된다더니 LS ELECTRIC 가격이 다르다"는 신고. 값은 맞았다 —
**갱신이 늦었다.**

```
06:30 UTC (15:30 KST)  국장 마감 — 종가 197,000 확정
07:30 UTC              data-sync 예약 시각
10:05 UTC (19:05 KST)  실제 시작 (스케줄러 155분 지연)
10:13 UTC (19:13 KST)  LS ELECTRIC 기록
```

그 **3시간 43분** 동안 화면은 전날 종가 188,400 을 보여줬고, 어디에도 "이건
어제 값"이라는 표시가 없었다. 사용자가 19시에 보고 틀렸다고 판단한 게 맞다.

### 고친 방식 — 두 갈래
**① 슬롯 다중화 (brief-*.yml 과 같은 패턴).** 마감 직후부터 45분 간격으로
시장별 슬롯 4개. 슬롯마다 지연이 독립적이라 하나쯤은 일찍 깨어난다. 각 슬롯은
`sync-gate` 로 "이 시장이 마지막 마감 세션보다 뒤처졌나"를 먼저 보고 아니면
즉시 끝낸다 — 표준 라이브러리만 쓰므로 `pip install` 앞에서 판정되고 건너뛰는
슬롯은 15초짜리다.

**뒤처진 시장만** 다시 만든다. 예전에는 두 실행이 매번 양 시장을 다 빌드해서
절반이 헛일이었다. 슬롯을 4배로 늘렸는데 하루 사용 분은 오히려 준다.

**② 화면이 기준일을 말한다.** 슬롯을 늘려도 공백은 항상 남는다 — 그러면 화면이
직접 말해야 한다.
- 종목 상세: 가격 옆에 `2026-08-04 마감`
- 시장 목록: 제목 옆에 `2026-08-04 마감 기준`
- 홈 지수 카드: 이미 `08.04 마감` (같은 날 추가)

### 짚어둘 것
게이트는 **표준 라이브러리만** 써야 한다. `pandas` 를 부르는 순간 건너뛰는
슬롯이 15초에서 1분이 되고, 슬롯을 여러 개 까는 이유가 사라진다.
`gate.data_stale` 이 `json` 으로 `index.json` 만 읽는 이유다.
