# 운영 가이드

## 1. 처음 한 번만 — 사용자 작업 체크리스트

### ① 텔레그램 봇 만들기

1. 텔레그램에서 **@BotFather** → `/newbot` → 이름·아이디 입력
2. 받은 **토큰** 복사 (`8123456789:AAF...`)
3. 만든 봇과 대화방 열고 아무 메시지나 전송 (필수 — 안 보내면 chat_id를 못 읽음)
4. chat_id 확인:

```bash
python -m pipeline.run telegram-whoami --token 여기에토큰
```

### ② Gemini API 키 발급 (무료)

https://aistudio.google.com/apikey → **Create API key** (`AIza...`). 무료 티어라
결제수단 없이 발급되고, 분당·일일 호출 한도 안에서 무료로 쓴다.

> 키가 없어도 파이프라인은 **규칙기반 요약 + 원문(미번역)으로 폴백**해서 정상 동작한다.
> 키를 넣으면 이벤트 해설 품질↑ + 해외뉴스 자동 번역이 켜진다.
> 모델을 바꾸려면 시크릿 `GEMINI_MODEL`을 설정한다 (기본 `gemini-2.5-flash`).

### ③ GitHub 시크릿 등록

```bash
gh secret set TELEGRAM_BOT_TOKEN --repo RuuNee/stock-pulse
gh secret set TELEGRAM_CHAT_ID   --repo RuuNee/stock-pulse
gh secret set GEMINI_API_KEY     --repo RuuNee/stock-pulse
```

(명령 실행 후 값을 붙여넣고 Enter)

### ④ 로컬 개발용 `.env`

레포 루트에 `.env` 생성 (`.gitignore`에 등록되어 커밋 안 됨):

```dotenv
TELEGRAM_BOT_TOKEN=8123456789:AAF...

```

### ④-1 여러 명에게 브리핑 보내기

`TELEGRAM_CHAT_ID`에 **콤마로 여러 개**를 넣으면 전원에게 발송된다. 하나만 넣으면
지금까지와 완전히 동일하게 동작한다.

```dotenv
TELEGRAM_CHAT_ID=123456789,987654321,-1001234567890
```

받을 사람마다 이 순서를 밟는다:

1. 상대가 텔레그램에서 봇을 찾아 **먼저 `/start`(또는 아무 메시지나) 전송**.
   텔레그램은 봇이 먼저 DM을 걸지 못하게 막아서, 이 단계 없이는 chat_id 자체가 안 잡힌다.
2. `python -m pipeline.run telegram-whoami` 로 chat_id 확인
   (여러 명이 잡히면 붙여넣기용 `TELEGRAM_CHAT_ID=...` 한 줄을 같이 출력한다).
3. `gh secret set TELEGRAM_CHAT_ID --repo RuuNee/stock-pulse` 로 콤마 목록 등록.

**그룹/채널로 보내는 방법**도 있다. 그룹을 만들어 봇을 초대하고 아무 메시지나 보낸 뒤
`telegram-whoami`로 나오는 **음수 chat_id**(예: `-1001234567890`)를 쓰면 된다.
인원이 많으면 개별 발송보다 이쪽이 관리하기 편하고, `/start` 절차도 필요 없다.

- 한 명이 실패해도(차단·`/start` 안 함·잘못된 ID) 나머지에게는 그대로 발송되고,
  실패한 chat_id가 로그에 남는다.
- 수신자 수는 `python -m pipeline.run doctor` 의 "시크릿" 항목에서 확인할 수 있다.

### ⑤ Vercel 배포

1. https://vercel.com → Add New Project → GitHub `RuuNee/stock-pulse` import
   (프라이빗 레포도 무료 플랜에서 연결된다)
2. 설정값 — 레포의 `vercel.json`이 이미 지정하고 있어 그대로 두면 된다:
   - Framework Preset: **Vite**
   - Root Directory: `web`
   - Build Command: `npm run build`
   - Output Directory: `dist`
3. Deploy → 발급된 도메인을 `pipeline/config.py`의 `SITE_URL`에 반영

> 배포된 뒤에는 사이트를 보려고 로컬 서버를 켤 필요가 없다. `start-web.bat`은
> 코드를 고칠 때만 쓰고, 평소에는 PC를 꺼도 폰·PC 어디서든 위 도메인으로 들어간다.
> Actions가 데이터를 커밋할 때마다 Vercel이 자동으로 다시 빌드한다.

### ⑦ 외부 스케줄러로 브리핑 정시 트리거

**왜 필요한가.** GitHub의 `schedule`은 최대 3~5시간 밀린다. 2026-08-07에는 슬롯
7개가 한 덩어리로 방출돼 국장 브리핑이 통째로 빠졌다([04-알림과스케줄](04-알림과스케줄.md)
참고). `workflow_dispatch`는 큐 지연이 없으므로, 외부 스케줄러가 정시에 이걸
때려 주면 지연 문제 자체가 사라진다. 스케줄 슬롯은 그대로 두고 백업으로 쓴다.

**1) PAT 발급** — https://github.com/settings/personal-access-tokens
- Fine-grained token → Repository access: `RuuNee/stock-pulse` 만
- Permissions → Repository permissions → **Actions: Read and write**
- 만료일을 적어 두고, 갱신도 달력에 넣는다 (만료되면 조용히 안 온다)

**2) cron-job.org 무료 계정** — https://cron-job.org → Create cronjob

국장용 / 미장용 두 개를 만든다.

| | 국장 | 미장 |
|---|---|---|
| URL | `https://api.github.com/repos/RuuNee/stock-pulse/actions/workflows/brief-kr.yml/dispatches` | `…/brief-us.yml/dispatches` |
| 시간대 | `Asia/Seoul` | `America/New_York` |
| 실행 | 월~금 **08:00** | 월~금 **08:30** |
| Method | `POST` | `POST` |

헤더 2개:
```
Authorization: Bearer <위에서 만든 PAT>
Accept: application/vnd.github+json
```

본문(Request body):
```json
{"ref": "main", "inputs": {"force": "false"}}
```

> ⚠️ `force`는 반드시 `"false"`. 빼거나 `"true"`로 두면 게이트를 통째로 건너뛰어
> **휴장일에도 브리핑이 나가고 중복 발송도 막지 못한다**. 문자열 `"false"`로 보내야
> 한다 — GitHub API는 dispatch inputs를 문자열로 받는다.

**3) 확인** — 성공하면 HTTP `204`가 떨어진다. `401`이면 PAT, `422`면 본문/브랜치명을
본다. 실제로 나갔는지는 Actions 탭의 `brief-kr` 실행 로그에서 게이트 판정 줄
("발송 창 안, 발송합니다")로 확인한다.

> 시각을 08:00 / 08:30으로 잡은 이유: 발송 창(07:45~08:40 KST · 08:15~09:10 ET)
> 한가운데다. 브리핑 생성이 1~3분이라 앞뒤로 여유가 남는다.

## 2. 명령어

```bash
# 소스 헬스체크 — 어떤 데이터 소스가 살아있는지 확인
python -m pipeline.run doctor

# 전체 데이터 재계산 (가격 + 뉴스 + 이벤트 + 요약) → data/
python -m pipeline.run sync

# 특정 시장만
python -m pipeline.run sync --market KR

# 브리핑 만들기 (발송 안 함, 콘솔 출력)
python -m pipeline.run brief --market KR --dry-run

# 브리핑 만들고 텔레그램 발송
python -m pipeline.run brief --market KR --send

# ⭐ 브리핑 나갔나 / 다음은 언제인가 — "왜 아직 안 와?" 할 때 먼저 이걸 본다
python -m pipeline.run status

# 지금 브리핑을 보내야 하는 시각인지
# 1행 true/false, 2행 발송 모드(ontime|late|skip), 판정 이유는 stderr
python -m pipeline.run gate --market KR

# 텔레그램 chat_id 조회
python -m pipeline.run telegram-whoami
```

## 4. 트러블슈팅

| 증상 | 원인 / 해결 |
|---|---|
| 텔레그램이 안 옴 | ① 봇과 대화를 먼저 시작했는지 ② 시크릿 오타 ③ Actions 로그 확인 ④ 휴장일이면 정상 동작 ⑤ **스케줄러 지연으로 모든 슬롯이 발송 창을 놓쳤는지** — 아래 참고 |
| 브리핑이 아직 안 옴 | **먼저 `python -m pipeline.run status`.** 브리핑은 하루 한 번 개장 직전 몇십 분에만 나가므로, 그 밖의 시간에는 "고장"과 "아직 때가 아님"이 겉보기에 같다. status 가 세션 일자·파일 유무·발송 창·게이트 판정·다음 발송 시각을 한 번에 보여준다 |
| 장전 브리핑이 그날 통째로 안 나감 | GitHub 스케줄러가 예약보다 최대 3시간 늦게 깨우는 게 원인. 슬롯 로그를 보고 어느 시각에 깨어났는지 확인한다. 지연이 240분을 넘었으면 `brief-*.yml` 앞쪽에 슬롯을 더 깔고 `tests/test_schedule.py`의 `MAX_DELAY_MIN`을 함께 올린다. 배경은 [10-전체기술스펙 §9.1.1](10-전체기술스펙.md) |
| `doctor`에서 피드 EMPTY | 해당 매체 RSS 폐지. `config.py` `FEEDS`에서 제거하고 [01-데이터소스.md](01-데이터소스.md) 갱신 |
| Google News 429 | 호출 과다. `GOOGLE_NEWS_DELAY_SEC` 상향 (기본 1.2초) |
| 이벤트 요약이 다 `rule` / 번역 안 됨 | `GEMINI_API_KEY` 미설정 또는 무료 쿼터 초과(429). Actions 로그의 `gemini` 라인 확인. 쿼터 초과면 다음 실행에서 자동 회복 |
| Actions에서 커밋 실패 | 레포 Settings → Actions → General → Workflow permissions → **Read and write** 체크 |
| 사이트에 옛날 데이터 | `data/` 커밋 후 Vercel 재배포됐는지 확인. 워크플로가 push하면 자동 트리거됨. 화면 상단에 "데이터가 N시간 전 것입니다" 배너가 뜬다(6시간 초과 시) |
| 로컬 dev 화면이 옛날 데이터 | dev 서버는 레포 `data/`를 직접 읽으므로 서버 재시작은 필요 없다. `data/` 자체가 낡은 것이니 `git pull` 또는 `python -m pipeline.run pulse` |
| `status`가 "브리핑 없음"인데 실제로는 나갔음 | 로컬 트리가 뒤처진 것. `status` 머리에 "로컬이 origin/main 보다 N커밋 뒤" 경고가 뜬다. `git pull` 후 다시 확인 |
| 종목 JSON이 없음 | `sync`가 실패했거나 유니버스에 없는 종목. Actions 로그 확인 |
| `git status`에 data/ 파일 수백 개 | 로컬에서 `sync`/`pulse`를 돌린 흔적. 전부 재생성 산출물이고 봇이 하루 12번쯤 같은 파일을 다시 올린다. `sync-data.bat` 하나로 정리된다(stash 후 pull). `install-sync-task.bat`으로 예약해 두면 손 안 대도 된다 |
| 예약 동기화가 안 도는 것 같음 | `.sync-data.log` 를 먼저 본다. 로그온해 있을 때만 실행되므로(`LogonType Interactive`) 로그아웃 상태면 건너뛴다. `schtasks /query /tn StockPulse-SyncData /v /fo list` 로 마지막 실행 결과 확인 |
| 예약 로그에 "pull 생략" 만 반복 | `data/` 밖에 커밋 안 한 코드 변경이 있다는 뜻. 의도된 동작이다 — 작업 중인 코드를 건드리지 않으려고 pull 만 건너뛴다. 커밋하거나 stash 하면 다시 받는다 |
| `.git` 폴더가 수십~수백 MB | 팩이 안 접힌 것. 이 저장소는 190개 JSON을 통째로 다시 커밋해서 로컬 팩이 빨리 쌓이는데 git 기본 `gc.autoPackLimit`(50)은 반응이 늦다. `sync-data.bat`이 임계값을 낮추고 `git gc --auto`를 돌린다. 실측: 106MB → 16MB |

```bash
python -m pipeline.run doctor
```

- 죽은 피드 정리 → `config.py` + `01-데이터소스.md` 동시 갱신
  (빠뜨리면 `pytest tests` 가 잡는다 — `tests/test_docs.py`)
- **"휴장일 표" 경고가 뜨면** `pipeline/util/dates.py` 의 `HOLIDAYS` 에 해당 연도를 추가.
  방치하면 그 해 공휴일에도 브리핑이 나간다
- GitHub Actions 사용량 확인 (Settings → Billing). 2026-08-04 시장별 게이트 도입 후
  추정 **~1,280분/월** (무료 2,000분). 종목이 184→291로 늘었는데도 줄었다 — 예전에는
  두 실행이 매번 양 시장을 다 빌드했고, 지금은 뒤처진 쪽만 돈다.
  내역: data-sync 국장 18분 + 미장 25분 × 22일 ≈ 946분 · pulse 288분 · 브리핑 ~50분.
  건너뛰는 슬롯은 15초라 무시해도 된다.
  **디버깅으로 `data-sync`를 수동 dispatch하지 말 것** — 브리핑 경로 확인은 리허설
  (`gh workflow run brief-kr.yml --ref main -f send=false`, 런당 1분)로 충분하다.
  실행 시간은 추정치다. 실측은 [06-백로그.md](06-백로그.md) B3 참고.
- Gemini 사용량 확인 (aistudio.google.com → 무료 티어 한도)
- `data/` 디렉터리 용량 — `brief/` 아카이브는 `BRIEF_KEEP_DAYS`(기본 30일) 기준으로
  브리핑을 쓸 때마다 자동 정리된다. 나머지(`tickers/`)는 종목 수에 비례할 뿐 시간이
  지나도 늘지 않으므로, 용량이 계속 커지면 유니버스가 늘어난 것이다
